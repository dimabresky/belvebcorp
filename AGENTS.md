# AGENTS.md — разработка belvebcorp

Инструкции для разработки проекта **belvebcorp** (корпоративный портал belveb) на Bitrix Framework. Следуй этому файлу, если пользователь явно не попросил иное. Для отдельного модуля действует его собственный `AGENTS.md`, если он есть.

## Платформа

Проект работает на **1С-Битрикс: Управление сайтом**, редакция **«Стандарт»**, ядро **≥ 26.800.0**.

- Пиши код в архитектуре Bitrix Framework: штатные модули, события, компоненты, агенты, опции модуля.
- Новый код использует **API ядра D7** (`Bitrix\Main` и пространства имён нужных модулей): `Loader`, `EventManager`, `Application`, ORM (`DataManager`), файловый и HTTP API ядра.
- Классы ядра и проекта подключай через `use`.
- Ядро, обновления и чужие модули не патчить. Поведение расширяй событиями, настройками или локальным модулем.
- Секреты (пароли, ключи API, `dbconn.php`, `.settings.php`) в репозиторий не класть. Их место — опции модуля на стенде или окружение.

## Принципы

### KISS

- Делай минимальное изменение, которое закрывает задачу.
- Повторяй соседний код проекта: имена, namespace, расположение файлов.
- Не добавляй фреймворк, контейнер зависимостей или слой абстракций, пока в задаче нет второй реализации.

### DRY

- Одна операция — одно место: сервис или публичный API модуля.
- Общие хелперы сайта собирай в одном классе `local/php_interface/include/classes/Utils.php`. Если он разрастается вокруг одной области, выноси отдельный `*Service`.
- Шаблон компонента показывает данные. Расчёты, очереди и интеграции живут в `php_interface` или в модуле.

### SOLID

- **S** — один класс отвечает за одну область. Обработчик события тонкий: читает данные события и вызывает сервис.
- **O** — новое поведение добавляется новым обработчиком, сервисом или модулем. Существующие классы не переписываются ради частного случая.
- **L (LSP)** — наследник и реализация сохраняют контракт базового типа: те же предусловия, тот же результат, без скрытых исключений и побочных эффектов. Реализации одного интерфейса взаимозаменяемы.
- **I** — интерфейс маленький. Клиент не реализует методы, которые ему не нужны. Интерфейс заводи только когда реализаций больше одной.
- **D** — сервис зависит от узкого контракта, а не от шаблона, `$_REQUEST` и глобального состояния. В `php_interface` приняты статические методы `*Events` / `*Service` / `Utils`. Конструктор — для новых нестатических сервисов модуля.

В `php_interface` роли такие:

| Суффикс | Роль |
|---------|------|
| `*Events` | обработчик события Bitrix |
| `*Service` | доменная операция |
| `*Agent` | агент и пакетная работа |
| `*Table` | ORM D7 (`DataManager`) |

### LSP

Подстановка типа обязательна и для своих классов, и для наследников API Битрикс. Метод с той же сигнатурой, что у `CModule` или `DataManager`, сохраняет видимость и смысл родителя. Вызывающий код работает с наследником так же, как с базовым классом.

## Куда класть код

Кастомный код сайта живёт в `local/`.

| Задача | Путь |
|--------|------|
| Шаблон сайта | `local/templates/belvebcorp/` |
| События, сервисы, агенты сайта | `local/php_interface/` |
| Общие хелперы | `local/php_interface/include/classes/Utils.php` |
| Автозагрузка своих классов | `local/php_interface/include/include.php` |
| Константы проекта | `local/php_interface/include/constants.php` |
| Значения окружения | `.env` в корне сайта |
| Регистрация событий | `local/php_interface/include/events.php` |
| Разовые скрипты, миграции, ручной запуск агентов | `local/tools/` |
| Точечные AJAX-эндпоинты | `local/ajax/` |
| Свои компоненты | `local/components/<namespace>/` |
| Модуль со своей установкой | `local/modules/<vendor>.<name>/` |

Класс вне модуля регистрируй в `Loader::registerAutoLoadClasses` внутри `include.php`. Каталог `php_interface` не является PSR-4-автозагрузкой.

`init.php` только подключает `include/include.php`. Автозагрузка живёт там. `include.php` подключает `constants.php` до регистрации классов и событий. Регистрация событий — в `include/events.php`. Реализация обработчиков — в классах `*Events`. Обработчики модуля остаются внутри модуля.

Модуль заводи, когда нужны установка и удаление, своя схема данных или отдельная версия. Код сайта без этого остаётся в `php_interface`.

Доступ к данным — через ORM D7 и Data-классы модулей (`Bitrix\Iblock`, `Bitrix\Main\ORM`). Компонент готовит данные для шаблона. `template.php` их выводит.

Стиль: PSR-1 и PSR-12. В модулях ещё и PSR-4: `lib/` соответствует namespace модуля. Один класс, интерфейс или трейт — один файл. Классы — `PascalCase`, методы — `camelCase`, константы — `UPPER_CASE`.

В шаблоне компонента `script.js`, `style.css` и языковые файлы подключаются ядром сами. Повторно их не подключай.

## Константы

Константы проекта определяются в `local/php_interface/include/constants.php`. Значение константы берётся из переменной файла `.env` в корне сайта. В `constants.php` одна функция читает переменную `.env` по имени; `define()` вызывает эту функцию.

```php
define('BELVEB_CATALOG_IBLOCK_ID', belvebEnvInt('BELVEB_CATALOG_IBLOCK_ID'));
```

- Имя константы и имя переменной в `.env` совпадают и пишутся в `UPPER_CASE`.
- Функция чтения — единственное место разбора `.env`. Код сервисов, компонентов и модулей использует константу.
- Обязательная переменная без значения останавливает подключение с понятной ошибкой. Необязательная читается отдельной функцией со значением по умолчанию. Целое число читается отдельной функцией и проверяется как целое.
- `.env` содержит секреты и стендовые идентификаторы и в репозиторий не входит. Список имён переменных без значений хранится в `.env.example`.

## Модули в `local/modules/`

Локальный модуль — полноценное решение Bitrix Framework, совместимое с редакцией «Стандарт» и ядром ≥ 26.800.0.

```text
local/modules/<vendor>.<name>/
  include.php
  options.php
  default_option.php
  install/
    index.php
    version.php
    db/mysql/install.sql
    db/mysql/uninstall.sql
  lib/
  lang/ru/
```

- Класс установки наследует `CModule`. `installDB`, `unInstallDB`, `installFiles`, `unInstallFiles` объявляй `public`, как в родителе.
- `DoInstall` / `DoUninstall` ставят и снимают модуль целиком: файлы, таблицы, события, опции, агенты.
- `unInstallDB` удаляет таблицы и опции, которые создал модуль.
- Классы лежат в `lib/`. Подключение — `use` и `Loader::registerAutoLoadClasses` (или карта в `include.php`).
- Таблицы — ORM D7. SQL установки и удаления лежит в `install/db/mysql/`.
- События модуля регистрируй через `\Bitrix\Main\EventManager` или `RegisterModuleDependences`. Обработчики остаются внутри модуля.
- Опции читай через API опций модуля. Значения по умолчанию — в `default_option.php`.
- Пользовательские строки — в `lang/ru/`.
- Публичные файлы копирует `installFiles()` и удаляет `unInstallFiles()`.

Имя модуля: `<vendor>.<name>` в нижнем регистре. Namespace в `lib/` — PascalCase от этого имени.

## Вёрстка и Vue

- Вёрстку собирай через **Tailwind CSS CLI** (`tailwindcss` / `@tailwindcss/cli`). Стили шаблона и компонентов задавай утилитами Tailwind. Отдельный ручной CSS пиши только там, где утилиты не закрывают задачу.
- Интерфейс компонентов Bitrix разрабатывай на **Vue, встроенном в Bitrix Framework** (BitrixVue). Подключение, компоненты, локализации, события и хранилище бери из ядра, а не из отдельной сборки Vue.
- Как это устроено: [Vue.js и Bitrix Framework](https://dev.1c-bitrix.ru/learning/course/index.php?COURSE_ID=176&INDEX=Y).

## Git и доставка

Основная ветка — **`main`**. Интеграционная ветка — **`dev`**.

```text
feat|fix|…  --PR-->  dev  --PR-->  main
```

1. Новая фича, исправление и любое другое изменение начинается с ветки от актуальной **`dev`** (`feat/…`, `fix/…`, `refactor/…`, `docs/…`, `chore/…`).
2. В **`dev`** код попадает только pull request из этой рабочей ветки.
3. В **`main`** код попадает только pull request из **`dev`**. Прямой pull request в `main` из рабочей ветки не открывать.
4. Коммиты — на английском, [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/).
5. Merge pull request — после зелёных проверок и явного подтверждения, если работает агент.
6. Удалённую рабочую ветку удаляй после успешного merge.

Прямых коммитов в `dev` и `main` нет. Force-push — только по явной просьбе.
